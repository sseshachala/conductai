# Audit 06 - Proposed Assertions

Plain-English assertions that would catch every P0 finding from Task 2 and Task 3. One per line. Each names the two or more surfaces it compares.

1. `/theguard/compliance` ASI-06 status derived from GET /guard/verify/evidence MUST NOT report "active" when GET /guard/verify/chain returns `valid=false` for the same workspace within the same 60s window (compares `/theguard/compliance` vs `/logs/guard` chain badge vs API `/guard/verify/evidence` vs API `/guard/verify/chain`).
2. `/theguard/compliance` ASI-03, ASI-04, ASI-07, and ASI-10 status MUST reflect at least one live signal (e.g. turn-budget config for ASI-03, RBAC seed for ASI-04, agent_role_id count for ASI-07, session-scan output for ASI-10) - none may be a hardcoded literal that ignores workspace state (compares rendered status on `/theguard/compliance` vs API `/guard/verify/evidence` source at verify.py:180-193 vs the underlying tables the status claims to describe).
3. The "Compliance packs" KPI count on `/governance` (governance/page.tsx:659, `installedPacks.length`) MUST equal the framework count in the same-page banner (governance/page.tsx:1084, `installed.length + bonus.length`), OR the two labels MUST disclose their differing filters to the user (compares KPI card vs hero banner on `/governance`).
4. The "N policies live across N frameworks" banner on `/governance` (governance/page.tsx:1084) sums `installed[*].rules_count + bonus[*].rules_count`, so the "N policies" figure MUST NOT be labeled as a distinct-rule count anywhere else in the product without disclosing the join-cardinality (compares `/governance` banner vs `/theguard/policies` "N active" line and Agent/Proxy tab totals).
5. All five rule tallies rendered on Guard surfaces MUST either agree, or each label MUST disclose the filter it applies (compares `/theguard` header "N agent - N proxy" vs `/theguard/policies` sub-header "N active" vs `/theguard/policies` Agent tab count vs Proxy tab count vs each pack tab count).
6. The delta rendered by KpiCard on `/governance` MUST satisfy `abs(delta_pct - round((value - avg_7d) / avg_7d * 100)) <= 1` for the value and avg_7d displayed on the same card (compares displayed value + displayed 7d avg vs displayed delta on `/governance` AI activity today and Risk intercepted today cards).
7. The chain-status wording MUST be identical across every surface that reads GET /guard/verify/chain: "Chain verified" / "Chain broken" on `/logs/guard` (page.tsx:404) vs "Chain intact" / "Chain broken" on `/governance` (page.tsx:1087) vs "Chain intact" / "Chain broken" on `/theguard/reports/soc2` (page.tsx:241) - all three surfaces must render the same string for the same boolean.
8. The "industry avg $15K each" clause on `/governance` (page.tsx:628) MUST be either sourced from a workspace-configurable value or explicitly labeled as an industry-benchmark constant (compares live `kpis.blocks_mtd` count vs the hardcoded "$15K" string in the same JSX line).
9. "Tool coverage" on `/theguard` (page.tsx:854, from GET /guard/developer-tools) and "Guard coverage" on `/theguard/discovery` (page.tsx:233, from GET /guard/discovery/summary) MUST NOT both be labeled "coverage" without disclosing what they cover (developers/machines vs discovered agents) - two surfaces, two entirely different objects, same word.
10. On any route where a card renders a delta percentage, the on-screen delta MUST be reconcilable with the on-screen value and 7d average - if the backend returns a delta_pct that cannot be derived from the returned value + avg_7d, the mismatch MUST be flagged (server-side vs client-side reconciliation of `/governance/kpis` response fields).
