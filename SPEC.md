# ConductAI Developer Agent Platform Spec · v1.0
Generated by Conduct SDD · 2026-06-09

## Project Overview
The ConductAI Developer Agent Platform is an agentic workflow system that provides pre-built, policy-governed AI agents for software development teams. Agents operate within configurable guard policies that enforce spend limits, token efficiency targets, and security constraints across multi-session development workflows. The platform steers developers toward responsible, cost-aware, and security-conscious use of AI tooling without blocking productivity.

---

## User Personas

- **Developer** — writes code daily, wants fast AI assistance, needs guardrails to avoid runaway spend or accidental data leakage
- **Senior Engineer / Tech Lead** — defines team-level agent workflows, reviews token and spend reports, tunes policies per project
- **Security Engineer** — authors and enforces security policies, audits agent interactions for sensitive data handling, reviews policy violations
- **Platform / DevOps Engineer** — deploys and operates the platform, manages integrations, monitors system health and quotas
- **Engineering Manager** — views spend dashboards, approves budget thresholds, receives policy violation summaries

## Functional Requirements

### Agent Catalog & Execution

**FR-001** Pre-Canned Agent Library
Agents must be available from a curated catalog of pre-built workflow agents (e.g., code review, test generation, vulnerability scan, documentation, refactor). Each agent encapsulates a specific development task as a reusable unit.
_Acceptance: A user can browse the catalog, select an agent by task type, and invoke it without writing any prompt or workflow configuration from scratch._

**FR-002** Agent Invocation Interface
The platform must expose a unified invocation interface (CLI, API, and/or IDE plugin entry point) through which any catalogued agent can be triggered with a target artifact (file, repo, PR, ticket).
_Acceptance: A developer can invoke any catalogued agent against a code file via at least one supported interface and receive a structured response within the session._

**FR-003** Multi-Step Agentic Workflows
Each agent must support multi-step execution where the output of one step can be used as the input to a subsequent step within the same workflow, without requiring manual handoff.
_Acceptance: A workflow containing at least two chained steps executes end-to-end automatically and produces a final consolidated output._

**FR-004** Session Continuity
Agent sessions must persist context across multiple interactions within a defined session window so that follow-up prompts reference prior context without the developer re-supplying it.
_Acceptance: A second prompt in the same session correctly references artifacts and decisions made in the first prompt without re-submission of context._

**FR-005** Agent Output Formats
Agents must return structured, machine-readable output (JSON or Markdown) alongside any human-readable summary, so downstream tools can consume results programmatically.
_Acceptance: Every agent response includes a structured payload that can be parsed by an automated test without string matching on prose._

### Guard Policies — Spend

**FR-006** Per-Developer Spend Limits
The platform must enforce configurable maximum token-spend budgets per developer per time period (daily, weekly, monthly), blocking or throttling further agent calls when the limit is reached.
_Acceptance: When a developer's spend reaches 100% of their configured limit, subsequent agent invocations are blocked and the developer receives a clear limit-reached message._

**FR-007** Per-Project / Per-Team Spend Limits
Spend limits must also be configurable at the project and team level, aggregating individual usage and enforcing a ceiling independent of per-developer limits.
_Acceptance: When aggregate team usage reaches the configured team limit, all team members' agent calls are blocked regardless of individual remaining budget._

**FR-008** Spend Threshold Warnings
The platform must emit a warning notification to the developer (and optionally their manager) when spend reaches configurable warning thresholds (e.g., 70%, 90%) before the hard limit is hit.
_Acceptance: A developer receives a warning at the configured percentage threshold before their session is blocked; the warning appears in-session and optionally via a notification channel._

**FR-009** Spend Override / Approval Workflow
An authorised approver (manager or senior engineer) must be able to grant a temporary spend extension for a developer or team without modifying the permanent policy.
_Acceptance: An approver can approve an override request; the developer's effective limit is raised for the specified duration and returns to the base policy afterward._

**FR-010** Spend Audit Log
Every token-consuming agent call must be recorded with developer identity, agent type, token count (prompt + completion), timestamp, and project context.
_Acceptance: An administrator can query the audit log and retrieve complete spend records for any developer or project within a specified date range._

### Guard Policies — Token Optimisation

**FR-011** Token Budget per Agent Call
Each agent type must have a configurable maximum token budget (prompt + completion) per single call; calls that would exceed the budget must be rejected before submission to the underlying model.
_Acceptance: An agent call whose estimated token count exceeds the per-call budget is rejected with a descriptive error before any tokens are consumed._

**FR-012** Prompt Compression / Summarisation
The platform must automatically compress or summarise long context inputs (e.g., large files, long conversation histories) to fit within token budgets before invoking the model, without requiring the developer to truncate manually.
_Acceptance: A file exceeding the raw token limit is automatically summarised to fit within budget; the agent still produces a valid, relevant response._

**FR-013** Cross-Session Token Optimisation
The platform must cache and reuse relevant prior-session context summaries to avoid redundant token consumption when the same artifacts are referenced in a new session.
_Acceptance: Re-invoking an agent on an unchanged artifact in a new session consumes fewer tokens than the initial invocation, verified by the audit log._

**FR-014** Token Efficiency Reporting
Developers and leads must be able to view per-agent, per-session token efficiency metrics (tokens consumed vs. configured budget, compression savings, cache hits).
_Acceptance: A dashboard or report shows token usage metrics broken down by agent type and session for a selected time range._

### Guard Policies — Security

**FR-015** Sensitive Data Detection
Before any prompt is sent to an underlying model, the platform must scan for and redact or block patterns matching sensitive data categories (API keys, passwords, PII, private IP ranges, internal hostnames) as defined in the active security policy.
_Acceptance: A prompt containing a string matching a configured sensitive pattern is either redacted (pattern replaced with a placeholder) or blocked, and the event is logged, before the model receives the payload._

**FR-016** Security Policy Authoring
Security engineers must be able to define, version, and publish security policies as structured configuration (pattern lists, severity levels, actions: redact | block | warn) without writing platform code.
_Acceptance: A security engineer creates a new policy version via the policy editor, publishes it, and subsequent agent calls enforce the new patterns within one policy-sync cycle._

**FR-017** Policy Assignment
Security policies must be assignable at the organisation, team, and project levels, with more specific policies overriding or extending broader ones.
_Acceptance: A project-level policy that adds a block rule is enforced for agents invoked in that project, while agents in other projects without that rule are unaffected._

**FR-018** Security Violation Alerting
Any security policy violation (block or redact event) must generate a real-time alert to the security engineer role and produce an audit record containing developer identity, agent type, matched pattern category, timestamp, and action taken.
_Acceptance: Within 60 seconds of a violation event, a security engineer receives an alert; the audit record is queryable and contains all required fields._

**FR-019** Output Security Scanning
Agent outputs must also be scanned against the active security policy before being returned to the developer, to prevent model-generated content from inadvertently surfacing sensitive information.
_Acceptance: An agent response containing a string matching a configured sensitive pattern is redacted or blocked before delivery to the developer._

**FR-020** Immutable Security Audit Trail
Security audit records must be append-only and tamper-evident, retaining all violation events for a configurable retention period (minimum 90 days default).
_Acceptance: An administrator cannot delete or modify a security audit record via any application interface; records remain queryable for at least the configured retention period._

### Policy Management & Governance

**FR-021** Policy-as-Configuration
All guard policies (spend, token, security) must be expressible as versioned configuration artefacts that can be stored in source control, diffed, and rolled back.
_Acceptance: Exporting a policy produces a file that, when re-imported, reproduces the identical policy state verified by a diff showing zero changes._

**FR-022** Policy Dry-Run Mode
Administrators must be able to activate a dry-run mode for any policy in which violations are logged and reported but enforcement actions (block/throttle) are not applied.
_Acceptance: With dry-run enabled, an agent call that would be blocked instead completes; a dry-run violation record is created and surfaced in the admin dashboard._

**FR-023** Policy Inheritance and Override
The platform must support a hierarchical policy model: organisation → team → project, where child-level policies can extend or selectively override parent policies without replacing them entirely.
_Acceptance: A child policy that overrides one rule inherits all other parent rules unchanged; both the override and inherited rules are enforced simultaneously._

### Observability & Reporting

**FR-024** Unified Dashboard
The platform must provide a web-based dashboard showing real-time and historical views of agent usage, spend consumption, token efficiency, and security violations, filterable by developer, team, project, and time range.
_Acceptance: A manager can filter the dashboard to a specific team and date range and see spend, token, and violation metrics refreshed within 30 seconds of filter application._

**FR-025** Exportable Reports
All dashboard data must be exportable in at least CSV and JSON formats for external analysis or compliance purposes.
_Acceptance: Clicking export on any filtered dashboard view produces a downloadable file in the selected format containing all rows visible in the current view._

**FR-026** Developer-Facing Usage Summary
Each developer must be able to view their own spend and token usage summary in real time, including remaining budget for the current period.
_Acceptance: A developer's personal usage view shows current-period spend, token consumption, and remaining budget, updated within 5 minutes of any agent call._

### Identity & Access Control

**FR-027** Role-Based Access Control (RBAC)
The platform must enforce RBAC with at minimum the following roles: Developer, Senior Engineer, Security Engineer, Platform Admin, and Manager, each with differentiated permissions on policy management, reporting, and overrides.
_Acceptance: A user with the Developer role cannot access policy authoring screens; a user with the Security Engineer role can access them. Verified by attempting access with each role._

**FR-028** Identity Federation
The platform must support authentication via enterprise identity providers using OIDC/SAML so that users do not require a separate platform credential.
_Acceptance: A user authenticates using their corporate IdP credentials and gains access to the platform without creating a platform-specific password._

**FR-029** API Key Management for Integrations
The platform must allow Platform Admins to create, rotate, and revoke API keys used by CI/CD or IDE integrations to call agent endpoints programmatically.
_Acceptance: An admin creates an API key, uses it to invoke an agent via the API, revokes the key, and subsequent calls with the revoked key are rejected with a 401 response._

### Integrations

**FR-030** IDE Integration
The platform must provide at least one IDE integration (VS Code extension or JetBrains plugin) that allows developers to invoke agents and view results without leaving their editor.
_Acceptance: A developer installs the extension, authenticates, invokes a catalogued agent on an open file, and views the structured result inside the IDE._

**FR-031** CI/CD Pipeline Integration
The platform must provide an API and example pipeline configuration enabling agent invocations (e.g., automated code review, security scan) to run as pipeline steps.
_Acceptance: An agent is invoked as a step in a sample CI/CD pipeline; the step passes or fails based on agent output and policy outcomes, with results retrievable via the audit log._

**FR-032** Source Control Context
Agents must be able to accept a repository URL and branch/commit reference as input context, fetching relevant file content automatically within token budget constraints.
_Acceptance: An agent invoked with a repo URL and commit SHA retrieves the relevant files, processes them within the token budget, and produces a response referencing content from that commit._

## Non-Functional Requirements

**NFR-001** Latency
Agent invocation round-trip time (from API call to structured response) must be under 30 seconds for the 95th percentile of calls under normal load, excluding model inference time beyond platform control.
_Acceptance: Load test at expected peak concurrency shows p95 latency ≤ 30 s._

**NFR-002** Availability
The platform API and dashboard must maintain 99.5% monthly uptime.
_Acceptance: Monthly uptime calculated from health-check monitoring is ≥ 99.5%._

**NFR-003** Scalability
The platform must support horizontal scaling to handle at least 500 concurrent agent sessions without degradation in latency or policy enforcement correctness.
_Acceptance: A load test simulating 500 concurrent sessions shows no policy bypass and p95 latency remains within NFR-001 bounds._

**NFR-004** Data Isolation
Agent session data, audit logs, and policy configurations for one organisation must be logically isolated from those of all other organisations.
_Acceptance: An authenticated user from Org A cannot retrieve any data records belonging to Org B via any API endpoint._

**NFR-005** Encryption at Rest and in Transit
All stored data (audit logs, session context, policies) must be encrypted at rest using AES-256 or equivalent. All data in transit must use TLS 1.2 or higher.
_Acceptance: Storage encryption is verified via infrastructure configuration audit; TLS version is verified via a TLS scanner against all public endpoints._

**NFR-006** Audit Log Integrity
Audit log writes must be durable — a write acknowledged to the caller must survive a single-node failure without data loss.
_Acceptance: Simulating a node failure immediately after a logged event shows the record is still present and queryable on recovery._

**NFR-007** Policy Enforcement Atomicity
Policy evaluation (spend check, token check, security scan) must complete before any tokens are sent to the underlying model; there must be no window in which a call proceeds without evaluation.
_Acceptance: Chaos testing that introduces latency into policy services shows calls are held, not bypassed, until policy evaluation resolves._

**NFR-008** Observability
The platform must emit structured logs, metrics, and distributed traces for all agent invocations, policy evaluations, and system errors, consumable by standard monitoring tooling.
_Acceptance: A monitoring stack can ingest platform telemetry and display an agent invocation trace from entry point to model call and back._

**NFR-009** Compliance Readiness
The platform must maintain audit records and access logs sufficient to support SOC 2 Type II evidence collection.
_Acceptance: A compliance review confirms all required log event types (access, change, violation) are present and queryable for any 90-day window._

## Out of Scope

- Payment processing, billing, or subscription management of any kind
- Building or hosting a proprietary LLM model — the platform integrates with external model providers
- General-purpose prompt playground or chat interface not tied to a structured agent workflow
- Human-in-the-loop task management or ticketing system
- Mobile (iOS/Android) native applications
- End-user (non-developer) facing products or consumer tooling
- Custom model fine-tuning or training pipelines
- Real-time collaborative editing or pair-programming tooling

## Open Questions

❓ **FR-002 / FR-030** — Which IDE(s) must be supported at launch vs. in a subsequent release? Prioritisation affects scope significantly.

❓ **FR-012** — Should prompt compression be model-agnostic (rule-based truncation/summarisation) or leverage a secondary LLM call? The latter has cost implications and must be weighed against the spend guard policies.

❓ **FR-015 / FR-016** — Should the platform ship a default set of sensitive-data patterns out of the box, or must security engineers define all patterns from scratch? Clarifying this determines onboarding complexity.

❓ **FR-009** — What approval channels are required for spend override requests (in-app only, email, Slack)? This drives integration scope.

❓ **FR-023** — When a child policy partially overrides a parent, should conflicts resolve by "most restrictive wins" or "child always wins"? This is a critical policy-semantics decision.

❓ **FR-031** — Which CI/CD platforms (GitHub Actions, GitLab CI, Jenkins, etc.) must have first-class example configurations at launch?
