Overview

Platform Overview

Conduct AI is a three-layer platform that sits between your engineering team and their AI coding tools. Think of it as MDM (Mobile Device Management) but for AI agents — the same mental model: policies push down, telemetry flows up, managers get visibility without touching developer machines.

LayerWhat it doesWho benefits
GuardIntercepts every AI tool call. Enforces team policies (block rm -rf, require approval for prod deploys, redact secrets). Captures session telemetry.Security leads, CTOs, compliance teams
Agent BoosterSemantic codebase routing. Returns only the relevant symbols for a task — not the whole file. 5–15× token cost reduction.Developers paying per token
Conduct RuntimeYAML playbook automation. 22 pre-built workflows covering GitHub, Slack, CI/CD, incident response. Chain AI brain blocks + tool calls + bash in a visual canvas.Engineering leads automating repetitive AI work
Why

Why We Built This

The problem

When a team goes from 1 developer using Claude Code to 20, three things break:

  1. Control — No way to prevent a junior dev from force-pushing to main or committing a .env file via AI suggestion
  2. Cost visibility — No one knows who's spending what on LLM tokens across 20 developers × 5 AI tools
  3. Audit trail — When something goes wrong ("who asked the AI to DROP TABLE?"), there's no log

Why not existing tools?

AlternativeGapHow Conduct fills it
GitHub branch protectionOnly protects git — doesn't intercept the AI agent before it actsHook fires before the bash command runs, not after
Pre-commit hooksOnly covers commits, not reads/writes/API callsIntercepts every tool type (bash, read, write, curl, edit)
Anthropic usage dashboardAggregate spend only, no per-developer or per-action breakdownPer tool call: who, what, which file, how many tokens, blocked or not
Custom MCP serversOne-off per team, no policy management UI, no cross-tool coverageSingle install covers Claude Code + Cursor + Codex + Windsurf
The insight: AI coding tools all support MCP (Model Context Protocol) — a standard for tool calls. We sit at the MCP layer. Every tool call passes through us before execution. That's the leverage point no existing product controls.

Guard

What Guard Does

Guard is the policy enforcement layer. It installs on every developer's machine in one command and intercepts every AI tool call before execution.

Developer runs: "git push --force origin main" inside Claude Code ↓ [PreToolUse hook fires — BEFORE execution] ↓ Load ~/.conductguard/policy.json (cached, 60s TTL) ↓ Match rule: "no-force-push" → action: BLOCK ↓ Return error to Claude Code: "🚫 Force push blocked. Coordinate with team." ↓ POST event to API (async, non-blocking) ↓ API → GuardAuditEvent inserted → Slack 🚨 fires → Dashboard updates

The key architectural principle: the decision is made locally (using a cached policy file) so there is zero network latency on the developer's flow. The telemetry is sent async after the decision. This means Guard works offline too.

Policy Matching Logic

for rule in policy["rules"]:
    if not rule["enabled"]:                          continue
    if tool_name not in rule["match_tool"].split(","): continue
    if rule["match_pattern"] and
       not re.search(rule["match_pattern"], input):  continue
    if rule["match_path_pattern"] and
       not re.search(rule["match_path_pattern"], path): continue
    if rule["match_tokens_before_gt"] and
       tokens_before <= rule["match_tokens_before_gt"]: continue

    return (rule["action"], rule["rule_id"], rule["message"])

return ("allow", None, None)
Design decision: Rules are evaluated top-to-bottom, first match wins. Order in YAML matters. Destructive ops are first so they can't be bypassed by a later rule. The match_tokens_before_gt field was added specifically for the "warn when context > 50K tokens" use case — a field type no other tool policy engine has.

Refresh Built-ins

Seeding only inserts missing rules (if exists: continue). When we add new rules to the YAML or update descriptions, existing workspaces don't get them automatically. The Refresh Built-ins button (POST /guard/policies/refresh-builtins) upserts all rules from YAML into the workspace — updating description, pattern, action, and message while preserving the admin's enabled/disabled toggle.

Policy caching strategy

Policy is cached locally to eliminate network latency from the critical path:

Startup:  Pull policy from /guard/policies/sync → save to ~/.conductguard/policy.json
Per call: Load policy.json (disk read, microseconds)
Every 60s: Background check policy version → if changed, re-download silently
Offline:  Stale policy.json used — Guard works without network
Why local cache? A network round-trip on every tool call would add 100–300ms to every bash command, read, and write. That's unusable. The 60-second staleness window is an acceptable trade-off — policy changes propagate within a minute, not instantly.

OS / IP / Hostname capture

Every event now includes machine fingerprint data — captured once per session on first event:

os_info:  platform.system() + platform.release() + platform.machine()
          → "Darwin 24.4.0 arm64"
hostname: platform.node()
          → "Sudhis-MacBook-Pro.local"
client_ip: Server captures from X-Forwarded-For header (Render proxy)
          → "203.0.113.42"

This solves the multi-machine problem: the same developer on two laptops now shows as two distinct sources in session reports.

Security

3-Layer PII Detection

All tool inputs are scanned before being written to audit logs or sent to the LLM. Detection runs in three ordered layers.

LayerWhat it catchesHowFalse positive risk
1. StructuralAWS access keys (AKIA*), GitHub tokens (ghp_, gho_, ghs_, github_pat_), PEM private keysHigh-confidence regex on unmistakable formatsZero — these formats are unique
2. Bare-in-textSlack tokens (xox*), OpenAI/Anthropic keys (sk-, ak-), Stripe keys (sk_live_*, rk_*), Bearer tokens, URL passwordsRegex on token prefixes without needing keyword contextVery low — prefixes are service-specific
3. Context-awareAny value ≥8 chars after a credential keyword (api_key, token, password, secret, auth, credential, access_key, etc.)Keyword + separator (= or :) + value regexLow — requires keyword context. Catches new services automatically.

Layer 3 keyword list

api_key | token | password | passwd | secret | auth | authorization |
credential | access_key | private_key | client_secret | client_id |
bearer | api_token | service_key
Why 3 layers? Layer 1 alone misses new services. Layer 3 alone produces false positives on code (e.g., headers["Authorization"] is not a credential). The layered approach gives zero false positives for known formats, near-zero for bare tokens, and acceptable catch-all for context-aware. Layer 3 also catches any new service (PyPI, npm, Vercel, Render, Twilio) without adding a new pattern — the keyword match is generic.

False positive fix (shipped June 2026)

Original separator: [=:"] — the " matched the closing quote of dict keys like headers["Authorization"]. Fixed to [=:] — only = and : trigger the context-aware layer. All 18 self-tests pass.

Security · Isolation

Row-Level Security

PostgreSQL RLS enforces workspace isolation at the database level — a misconfigured query can't accidentally leak another tenant's data.

-- Migration 0004
ALTER TABLE guard_policies ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON guard_policies
  AS PERMISSIVE FOR ALL
  USING (workspace_id = current_setting('app.current_workspace', true)::uuid);

-- Set per request in middleware:
db.execute("SET LOCAL app.current_workspace = :ws", {"ws": workspace_id})

Applied to: guard_policies, guard_sessions, audit_log, workflows, conduct_api_keys.
Not applied to: runs (the worker needs cross-workspace visibility to execute queued jobs).

Agent Booster

What Agent Booster Does

Agent Booster replaces full file reads with semantic symbol retrieval. Instead of sending 2000 lines of executor.py to the LLM, it sends only the 80-line function that's relevant to the task.

Without BoosterWith Booster
Read executor.py (1778 lines = ~45K tokens)smart_read("executor.py", "how blocks handle errors") → 3 functions = ~800 tokens
Grep for "GuardSession" across codebasesearch_context("GuardSession usage") → 5 relevant symbol slices
Read file to see what functions existget_symbols("models.py") → list of 20 function/class names, no content
Always use Opus (expensive)route_model("fix typo in comment") → haiku (10× cheaper)

Typical savings: 70–95% token reduction on file reads, 5–15× cost reduction via model routing.

Agent Booster · Architecture

4-Layer Architecture

Layer 1 — Symbol Index

indexer.py
├─ tree-sitter: parse .py / .ts / .tsx / .js / .jsx
├─ Extract: functions, classes, methods → {name, start_line, end_line, kind}
├─ SQLite store: .booster/symbols.db
└─ File hash + mtime: skip re-indexing unchanged files

Layer 2 — Vector Embeddings

indexer.py → _embed_for_index()
├─ Model: all-MiniLM-L6-v2 (local, 384-dim, ~25MB)
├─ No data leaves the machine
├─ Storage: SQLite BLOB (normalized L2 vectors)
└─ Prefix: "passage: " for indexing, "query: " for retrieval

Layer 3 — Smart Retrieval

retriever.py
├─ Input: file path + task description
├─ Keyword search: BM25-style token match on symbol names
├─ Vector search: cosine similarity on embeddings
├─ Fusion: Reciprocal Rank Fusion (RRF) combines both scores
└─ Output: only matching symbol line ranges (sliced from file)

Layer 4 — SmartCrusher

crusher.py
├─ Threshold: 2048 bytes (don't compress small outputs)
├─ Strategy 1: JSON array → keep head[5] + tail[3], collapse middle
├─ Strategy 2: Consecutive repeated lines → "// … N identical lines omitted"
└─ Never returns larger than input
Why local embeddings? Sending codebase content to an embedding API (OpenAI, Cohere) risks leaking proprietary code. The all-MiniLM-L6-v2 model runs locally in ~80ms, produces vectors good enough for retrieval, and requires no API key or network access.

Cache alignment (P0 — June 2026)

Anthropic's prompt cache uses the first 1024 tokens as a stable prefix. If tool schemas arrive in different orders across requests, the cache prefix changes and you pay full price every time.

Fix: mcp_server.py sorts tools alphabetically + sorts schema keys
     → Stable schema hash → Anthropic KV cache hit on every request
     → ~30% cost reduction on repeated tool calls in long sessions

Compiler + Executor

Compiler (compiler/compiler.py)

Turns a human-written playbook description into structured Brain block prompts.

Step 1 — Extraction (Claude Sonnet, single-turn)
  Input:  "Extract and fix all unused imports in src/lib/*.ts"
  Output: { goal, constraints, output_format } (structured)

Step 2 — Template assembly
  system_prompt = brain_prompt(
    goal="Identify and remove unused imports",
    constraints=["Match TypeScript import statements", "Preserve type imports"],
    output_format="List of removed import statements",
    max_turns=3
  )

Executor (runtime/executor.py, 1778 lines)

Orchestrates playbook run execution. Manages state, branching, token budgets, and block-level retries.

execute_run(run_id):
  while state.current_block:
    block = load_block(state.current_block)
    result = execute_block(block, state)    # brain|bash|tool|output|logic
    state.record_event(block.id, result)
    state.current_block = graph.next(current_block, result.decision)
  finalize_run(state)
Why YAML playbooks? Engineers already understand YAML (CI/CD pipelines, Kubernetes configs). A playbook that calls GitHub, Slack, and runs bash is readable and version-controllable. No visual canvas required to create one — the canvas is just a viewer/editor on top of the YAML.
